## 4. How the bench measures

1. Two copies of the same code: Echo's frozen 5c5d4a4 copy and the product at the head, compiled with the same settings.
2. Paired rounds that alternate the copies, with a full collection before each round.
3. The timing thread is pinned, not the process. With the whole process pinned to one processor, the runtime's background tiering thread shared that processor with a Highest-priority timing loop, so each copy reached optimized code at a random time. Measured 2026-11-11, net10, one row per fresh process: tdes.encrypt-block 11,908 ns with the process pin, 2,326 ns with tiering off, and 2,496 to 2,724 ns with the thread pin. Every same-code result taken with the process pin is void.
4. The balanced crossover. Two harness effects exist on this machine, and neither comes from the code:
   - Position: on net10 the copy timed as "new" ran AES encrypt-block about 12% faster, whichever copy it was (1.110 to 1.125 normal order, 1.122 to 1.142 swapped).
   - JIT order: on net48 the copy compiled second ran SHA-256 about 5% faster.
   So every host runs 4 processes. normal1 and swapped1 compile the frozen copy first; normal2 and swapped2 compile the product first; swapped times the product as "original".
   - N = sqrt(N1 x N2) and S = sqrt(S1 x S2), where a position ratio is original ns / new ns.
   - Code ratio = sqrt(N / S). Position bias = sqrt(N x S).
   - Pair bias k = sqrt(Nk x Sk). Drift = pair bias 1 / pair bias 2. A drift outside 0.90 to 1.10 fails the run.
   - The same-code band and the AO rows read the code ratio only.
   - A self-check with a known answer (bias 1.12, JIT factor 1.36, code 1.05) runs before every combine.
5. Load gates, tuned to this desktop (data in section 6):
   - Settle: three 1-second readings of outside load within 5 points of each other.
   - Whole machine: a pair fails above max(settle baseline, 25%) + 15 points.
   - Timing core: a pair fails above 25% outside load on the pinned core and its hyper-thread sibling.
   - A refused step runs up to twice more; a third refusal stops the run.
6. Every row prints the processor of the timing thread before and after the case. Every row in this run read `14>14`.

## 5. SHA-256 on 32-bit CLR 2.0: a finding for CE users

On 32-bit CLR 2.0 the speed of the same SHA-256 code moved by up to about 37% with the process alone. CLR 2.0 x86, normal order, frozen copy compiled first, same code in both copies:

| Fresh process (2026-11-11) | sha256.update | hmac-sha256 |
|---|---:|---:|
| A | 1.357 | 1.374 |
| B | 0.729 | 0.729 |

Ratio = frozen ns / product ns in that process. In the same processes the AES, TDES and GCM rows stayed within 0.925 to 1.091. In this Job T, CLR 2.0 x86 sha256.update read a code ratio of 1.000, so the swing does not appear in every process. CLR 2.0 x64 read 0.978 to 1.023 on every row on 2026-11-11. On net48 the effect is about 5% and follows JIT order.

A CE device runs a 32-bit JIT with no tiering. A SHA-256 or HMAC timing from one process on such a runtime can be off by a third in either direction.

The rule for S0 and S1: on net48 and CLR 2.0 x86 and x64, sha256.update, sha256.message, hmac-sha256 and the file rows that run them are report only. They print with every process's ratio and process id and stay outside the band and drift checks. net10 SHA-256 stays gated.

The condition for S3: before any S3 code, the bench gets a many-process SHA-256 measurement (12 fresh processes per host, the median per-process code ratio, the spread printed), and its falsifier must put the CLR 2.0 x86 SHA-256 median inside 0.90 to 1.10. If it cannot, the swing is too wide to judge an S3 change of 5 to 10%, and that is decided before S3 starts.

Whole-machine maximum on a refused step: 41.4% to 59.0%. Every step that passed stayed at or under 25% on the timing core, because the gate refuses above it.
